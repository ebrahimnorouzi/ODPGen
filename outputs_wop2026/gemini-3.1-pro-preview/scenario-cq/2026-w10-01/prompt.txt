You are an ontology engineer. Generate an OWL ontology design pattern (ODP) in Turtle syntax using both the scenario and competency questions below.

Requirements:
- Prioritize semantic faithfulness to the scenario.
- Ensure the ODP structurally supports every CQ (the classes and properties needed to answer each CQ must be present).
- Do not add concepts or axioms not grounded in the scenario or CQs.
- Declare every class with `a owl:Class`, every property with `a owl:ObjectProperty`, `a owl:DatatypeProperty`, or `a owl:AnnotationProperty`.
- Do NOT create individual instances (e.g. `:SomePerson a :Person`); output schema axioms only.
- Add rdfs:label and rdfs:comment annotations to every class and property.
- Declare a mandatory ontology header: `:Ontology a owl:Ontology ; rdfs:label "..." ; rdfs:comment "..." .`

Use these standard prefixes (declare all that you use):
  @prefix owl:  <http://www.w3.org/2002/07/owl#> .
  @prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
  @prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
  @prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .
  @prefix :     <http://example.org/odp#> .

Output format — strictly in this order, nothing before item 1:
1. The complete Turtle ontology wrapped in a ```turtle ... ``` code block. Output this FIRST, before any explanation.
2. Scenario-requirement-to-axiom mapping: for each requirement extracted from the scenario, identify the axiom(s) that encode it.
3. CQ-to-axiom mapping: for each CQ, list the classes and properties that enable answering it.
4. Intentionally excluded concepts: list any scenario concepts left out and why.

Scenario:
This example is motivated by a concrete use case from the SMARTY research project, which focuses on scalable and quantum-resilient heterogeneous edge computing enabling trustworthy AI, and includes a specific activity that addresses the semantic management of digital assets (including software) for supporting interoperability. In the context of one of the use cases of the project, a matchmaker is being developed, which addresses the dynamic allocation of hardware resources (DPU and GPU) based on the characteristics and requirements of incoming service requests, by comparing the requirements expressed for a given software with the actual characteristics of software and hardware resources described in a catalogue. The goal of the matchmaker is to identify candidate resources that can be used to execute, support, or deploy the main software.

Competency Questions:
- Which is the (software/hardware) requirement of a software?
- Which is the software/hardware required by a software?
- Which is the type of software/hardware required by a software?
- Which is the required (minimum/maximum/exact) value of a property of a software/hardware required by a software?
- Which is the required (maximum/minimum/exact) version of a software required by a software?
