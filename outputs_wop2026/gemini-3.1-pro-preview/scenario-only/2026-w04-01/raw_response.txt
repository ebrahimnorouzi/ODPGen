    rdfs:comment "A binary or executable file being analyzed or reverse engineered." .

    rdfs:comment "A data structure collected from a binary file containing symbols used in the executable." .

    rdfs:label "Symbol" ;
    rdfs:comment "A representation of data extracted from a binary file, which may have lost its original name during disassembly." .

:SoftwareSupplyChain a owl:Class ;
    rdfs:label "Software Supply Chain" ;
    rdfs:comment "The network of components, dependencies, and artifacts that make up a software ecosystem." .

:DependencyVulnerability a owl:Class ;
    rdfs:label "Dependency Vulnerability" ;
    rdfs:comment "A security vulnerability found within the dependencies of a software supply chain." .

:MalwareBehavior a owl:Class ;
    rdfs:label "Malware Behavior" ;
    rdfs:comment "Specific malicious actions or behaviors exhibited by a software artifact." .

### Documentation

**Intent:**
To model the structure of reverse-engineered software artifacts, their symbol tables, and the relationships between internal symbols, while extending to detect dependency vulnerabilities and malware behaviors within a broader software supply chain.

**Covered requirements:**
*   Modeling binary/executable files (`SoftwareArtifact`) and their extracted `SymbolTable`.
*   Representing symbols as either a `Function` or a `Variable`.
*   Capturing the naming state of symbols through `hasOriginalName` and user-defined `hasRenamedLabel`.
*   Visualizing how symbols fit and work together via the `interactsWith` property.
*   Connecting artifacts to a `SoftwareSupplyChain`.
*   Identifying `DependencyVulnerability` instances within the supply chain.
*   Linking `MalwareBehavior` to artifacts and using it to indicate vulnerabilities across the supply chain.

**Known assumptions and exclusions:**
*   **Tooling Exclusion:** The ontology assumes reverse engineering tools (like Ghidra) are the implicit source of the symbol table, but does not model the software tool itself as a class to keep the schema focused strictly on the resulting data graph.
*   **Process Exclusion:** The specific mechanics and stages of disassembly and decompilation processes are excluded, as the scenario focuses on the resulting knowledge graph of the data.
*   **Symbol Types:** The pattern assumes a symbol is either a function or a variable (and makes them disjoint). While real-world binaries contain other symbol types (e.g., sections, imports), they are excluded to strictly adhere to the provided scenario scope.
