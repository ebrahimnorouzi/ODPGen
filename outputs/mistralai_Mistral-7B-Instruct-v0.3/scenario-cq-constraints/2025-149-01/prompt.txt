You are an ontology engineer. Generate an OWL ontology design pattern (ODP) in Turtle syntax from the scenario and competency questions below, then self-validate the output against the checklist.

Use these standard prefixes (declare all that you use):
  @prefix owl:  <http://www.w3.org/2002/07/owl#> .
  @prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
  @prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
  @prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .
  @prefix :     <http://example.org/odp#> .

Modeling constraints:
- Do not add concepts or axioms not grounded in the scenario or CQs.
- Every class and property must have rdfs:label and rdfs:comment annotations.
- Declare a mandatory ontology header: `:Ontology a owl:Ontology ; rdfs:label "..." ; rdfs:comment "..." .`
- Keep the ontology minimal and reusable.

Self-validation checklist (evaluate each item as PASS or FAIL with a one-line reason):
1. Turtle syntax is valid (no missing dots, brackets, or semicolons).
2. All prefixes used in the body are declared at the top.
3. Every property with a domain or range declaration uses only classes defined in this ontology or well-known external vocabularies.
4. No two classes or properties are defined with contradictory restrictions (e.g., disjoint yet subclass, or domain A yet also domain B inconsistently).
5. Every CQ is traceable to at least one class or property in the ontology.
6. No concept appears in the ontology that is not grounded in the scenario or CQs.

Output format (strictly in this order):
1. Turtle ontology wrapped in a ```turtle ... ``` code block.
2. Validation report: checklist items 1–6 each marked PASS or FAIL with a brief reason.
3. Scope report: (a) requirements from the scenario that are covered, (b) any scenario concepts explicitly excluded and why.

Scenario:
securing access to a relational database (RDB) queried via Structured Query Language (SQL).

Competency Questions:
- Can the ontology represent a relational database as a first-class schema entity?
- Can the ontology represent tables belonging to a database?
- Can the ontology represent columns belonging to a table?
- Can the ontology represent primary-key relationships in the schema?
- Can the ontology represent foreign-key relationships and distinguish same-named columns across different tables when they are not semantically linked?
- Can the ontology define a policy for a specific agent?
- Can a policy specify a high-level ReadAction?
- Can a policy specify a high-level ModifyAction?
- Can a policy specify a ViewActionScope for read operations?
- Can a policy specify a ProcessActionScope for read operations?
- Can a policy be defined at table level?
- Can a policy be defined at column level?
- Can a policy be defined at row level using conditions?
- Can the ontology express a prohibited modify action on a table?
- Can the ontology express a table-level read prohibition for processing?
- Can the ontology express a table-level read prohibition for viewing?
- Can the ontology express a conditional row-level read restriction for later enforcement?
- Can the ontology represent a SQL query as an AST-based semantic graph?
- Can a SQL statement such as SelectStatement or UpdateStatement be mapped to its semantic action type?
- Can a query statement be linked to the executing agent?
- Can SQL clauses be assigned operational scopes such as view or process?
- Can scope be propagated to reference nodes as an effectiveActionScope?
- Can a TableRef in the query be linked to its corresponding schema Table?
- Can a ColumnRef in the query be linked to its corresponding schema Column?
- Can the reasoner infer whether a referenced table or column is Violated or RowTag based on the matching policy, action, and scope?
