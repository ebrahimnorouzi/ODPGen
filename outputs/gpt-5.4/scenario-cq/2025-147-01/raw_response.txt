4. Intentionally excluded concepts

- AIS as a separate class
  - Excluded because the scenario mentions AIS tracks as a source, but the CQs only require trajectory/route support, not explicit source-system modeling.

- Registry database, classification society database, onboard monitoring platform as separate classes
  - Excluded because they are named as example data systems, but no CQ asks to model source systems themselves.

- Logistics, fleet management, monitoring, research, SAR, digital twin, and life cycle simulation as process/use-case classes
  - Excluded because they motivate the ontology but are not themselves queried in the CQs.

- GPS antenna as a separate physical component class
  - Excluded because the CQ only requires relative placement values; dedicated component modeling is not necessary.

- Explicit “German flag” individual
  - Excluded because individuals are forbidden and schema only is requested; `:Country` plus `:registeredUnderFlag` structurally supports such data.

- Explicit engine categories such as electric engine, diesel engine, etc.
  - Excluded as named classes because the scenario/CQs ask for engine types generally, but do not ground a fixed taxonomy. This is supported via `:EngineType`.

- Explicit route prediction model or forecasting method
  - Excluded because the CQ only asks for predicted route, not how prediction is produced.

- Explicit acoustic signature class distinct from sonar data
  - Excluded because `:SonarData` is sufficient for the sonar-related CQs.

- Detailed geospatial coordinate model
  - Excluded because the scenario/CQs ask for typical location and route/trajectory information, but do not require coordinate geometry constructs.

- Detailed interconnection topology among propulsion components beyond basic relations
  - Excluded because only the existence of propulsion systems, technologies, engines, fuels, driven components, and assistance relations is grounded by the scenario and CQs.
