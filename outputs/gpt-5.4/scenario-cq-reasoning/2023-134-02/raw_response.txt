1. **Reasoning for steps 1–6**

### Step 1. Atomic requirements
- R1. The ontology must represent actors involved in a Solid setting and their roles or kinds of participation.
- R2. The ontology must represent providers of Pods and applications/services as identifiable entities.
- R3. The ontology must represent Pod infrastructure metadata, including specification/version information and installed functionality.
- R4. The ontology must represent categories of data and where such data is stored in a Pod.
- R5. The ontology must represent data handling practices and data needed by apps/services.
- R6. The ontology must represent user-expressed privacy policies or preferences.
- R7. The ontology must represent records/logs for accountability and provenance.
- R8. The ontology must represent consent records and data access/use events.
- R9. The ontology must represent changes to data handling policies.
- R10. The ontology must support legal compliance and auditing by representing actionable records about data interactions.
- R11. The ontology must represent the type of action performed on data.
- R12. The ontology must represent the entity interacting with data.
- R13. The ontology must represent the entity publishing a log.
- R14. The ontology must represent when a log was issued.
- R15. The ontology must represent where data is stored.
- R16. The ontology must represent the application/service used to generate data, if any.

### Step 2. Candidate classes and properties
- For R1/R2/R12/R13:
  - Classes: `:Agent`, `:Role`, `:Provider`, `:PodProvider`, `:AppProvider`
  - Properties: `:hasRole`, `:interactingEntity`, `:publishedBy`
- For R3:
  - Classes: `:Pod`, `:Specification`, `:Functionality`
  - Properties: `:runsSpecification`, `:hasInstalledFunctionality`, `:providesPod`
- For R4/R15:
  - Classes: `:DataResource`, `:DataCategory`, `:StorageLocation`
  - Properties: `:hasDataCategory`, `:storedIn`
- For R5/R9:
  - Classes: `:DataHandlingPolicy`, `:PrivacyNotice`
  - Properties: `:hasPolicy`, `:hasPrivacyNotice`, `:declaresRequiredDataCategory`
- For R6:
  - Class: `:PrivacyPreference`
  - Property: `:hasPrivacyPreference`
- For R7/R8/R10/R11/R12/R13/R14/R16:
  - Classes: `:LogEntry`, `:DataInteraction`, `:ActionType`, `:Application`
  - Properties: `:recordsInteraction`, `:hasActionType`, `:aboutData`, `:issuedAt`, `:usedApplication`
- For R8:
  - Class: `:ConsentRecord`
  - Possible property: `:recordsConsentFor` (later removed as unnecessary if not needed by CQs)

### Step 3. Draft axioms
- Core actor axioms:
  - `:Provider rdfs:subClassOf :Agent`
  - `:PodProvider rdfs:subClassOf :Provider`
  - `:AppProvider rdfs:subClassOf :Provider`
  - `:hasRole` domain `:Agent`, range `:Role`
  - `:interactingEntity` domain `:DataInteraction`, range `:Agent`
  - `:publishedBy` domain `:LogEntry`, range `:Agent`
- Infrastructure axioms:
  - `:providesPod` domain `:PodProvider`, range `:Pod`
  - `:runsSpecification` domain `:Pod`, range `:Specification`
  - `:hasInstalledFunctionality` domain `:Pod`, range `:Functionality`
- Data/storage axioms:
  - `:hasDataCategory` domain `:DataResource`, range `:DataCategory`
  - `:storedIn` domain `:DataResource`, range `:StorageLocation`
- Policy/privacy axioms:
  - `:hasPolicy` domain `:Agent`, range `:DataHandlingPolicy`
  - `:hasPrivacyNotice` domain `:Agent`, range `:PrivacyNotice`
  - `:declaresRequiredDataCategory` domain `:Application`, range `:DataCategory`
  - `:hasPrivacyPreference` domain `:Agent`, range `:PrivacyPreference`
- Logging/provenance axioms:
  - `:DataInteraction rdfs:subClassOf` restrictions:
    - exactly 1 `:hasActionType` some `:ActionType`
    - exactly 1 `:interactingEntity` some `:Agent`
    - exactly 1 `:aboutData` some `:DataResource`
    - max 1 `:usedApplication` some `:Application` (optional app)
