Overview & Research Questions

ODPGen evaluates how well LLMs generate Ontology Design Patterns (ODPs) — reusable OWL ontology templates — from natural-language scenarios and competency questions.

Research Questions

  • RQ1 — How well can LLMs generate valid OWL/Turtle from scenarios?
  • RQ2 — How logically consistent and error-free are the outputs?
  • RQ3 — What is the impact of prompting strategy?
  • RQ4 — How faithful are outputs to the ground-truth scenario?
  • RQ5 — Can models generalize to recently published ODPs?

Worked Example — Scenario 2023-133-01: Causal Bayesian Network

Scenario Text

The sprinkler use case is a well-known example from the CBN literature. A CBN reasons about the cause of a slippery pavement. Five nodes represent events: rainy season, sprinkler on, raining, pavement wet, pavement slippery. Directed edges carry effect weights — e.g., rainy season → rain with weight 0.6. Rain→slippery is mediated by pavement being wet.

Competency Questions (4 CQs)

  1. What events are responsible for the pavement being slippery?
  2. What would be the outcome of turning the sprinkler on/off?
  3. How strong is the causal link between sprinkler and wet pavement?
  4. If the pavement is not wet, how does that affect it being slippery?

Ground-Truth ODP Structure (Expert-Authored)

5 classes · 5 object properties · reification pattern

  • Classes: Event, AbstractEvent, ConcreteEvent, Causes, EffectWeight
  • hasTreatment, hasOutcome (Causes→Event)
  • hasMediator (Causes→Event — captures indirect causation)
  • hasEffectWeight (Causes→EffectWeight)
  • ofType (ConcreteEvent→AbstractEvent)

Key design: Causes is a class (reification), not a property — enables weight and mediator to be attached to the relation itself.

Different conceptualization: introduces intermediate categories (WeatherEvent, PavementCondition) not in ground truth or scenario. More superfluous elements.

Systematic finding: Both models literalize the sprinkler scenario into domain-specific class hierarchies. The expert-authored ODP is abstract and reusable (no sprinkler/rain classes) — it uses reification to make causal relations first-class objects. LLMs struggle to generate this level of abstraction from narrative alone.

Prompt Templates — Actual Text Sent to Models

Config 1 — scenario-only

You are an ontology engineer. Generate an OWL
ontology design pattern (ODP) in Turtle syntax
from the scenario below.

Requirements:
- Stay strictly within the scenario scope.
- Use clear, self-explanatory class/property names.
- Include minimal but sufficient axioms.
- Declare every class with `a owl:Class`, every
  property with the appropriate OWL type.
- Do NOT create individual instances.
- Add rdfs:label and rdfs:comment to all entities.
- Declare: :Ontology a owl:Ontology ; rdfs:label
  "..." ; rdfs:comment "..." .

@prefix owl:  <...owl#> .
@prefix rdf:  <...rdf-syntax-ns#> .
@prefix rdfs: <...rdf-schema#> .
@prefix xsd:  <...XMLSchema#> .
@prefix :     <http://example.org/odp#> .

Output — in this order:
1. Turtle ontology in ```turtle ... ``` block.
2. Documentation: Intent · Requirements · Assumptions.

Scenario:
{SCENARIO_TEXT}

Config 5 — scenario-cq-reasoning (best faithfulness)

You are an ontology engineer. Create an OWL ODP
in Turtle syntax.

Before writing, reason through these steps
internally (do NOT write them out yet):
1. Extract atomic requirements from the scenario.
2. Propose candidate classes/properties per req.
3. Draft axioms (subclass, domain, range, card.).
4. For each CQ, verify which axioms answer it.
5. Add/refine axioms to cover uncovered CQs.
6. Remove entities not traceable to any req/CQ.

Constraints:
- schema axioms only (no instances)
- rdfs:label + rdfs:comment on every entity
- owl:Ontology header mandatory
- minimal and reusable; no facts beyond scenario/CQs

Output — strictly in this order:
1. Complete Turtle in ```turtle ... ``` block.
2. Reasoning summary: one bullet per step 1–6.
3. Traceability table: requirement/CQ → axiom(s).

Scenario: {SCENARIO_TEXT}
CQs: {CQ_LIST}
Config 3 (scenario-cq) adds scenario→axiom and CQ→axiom mapping tables to the output. Config 4 (scenario-cq-constraints) adds a 6-item self-validation checklist (syntax, prefixes, domain/range, coherence, CQ coverage, scope). All configs enforce temperature=0.0.

Prompting Strategies — 5 Configurations

1. scenario-only

Model receives only the domain scenario text. No CQs. Must infer scope from narrative alone. Highest scenario vocabulary coverage.

2. cq-only

Model receives only the Competency Questions. No scenario text. Highest CQ coverage but also highest hallucination.

3. scenario-cq  [Balanced]

Both scenario text and CQs. Model must produce scenario→axiom and CQ→axiom mapping tables.

4. scenario-cq-constraints  [Validation]

Extends scenario-cq with a 6-item self-validation checklist before output.

5. scenario-cq-reasoning  [Best Faithfulness]

Explicit 6-step internal reasoning: extract requirements → propose classes → draft axioms → verify CQs → remove unsupported → output ODP. Lowest hallucination overall. Also produces a reasoning summary and traceability table (requirement/CQ → axiom).

Evaluation Methodology — 4 Layers

Layer 1 — Formal / Syntactic Quality

  • parse_success — Valid Turtle syntax?
  • triple_count — Total RDF triples
  • ontology_declared — owl:Ontology header?
  • label_coverage_ratio — All entities with rdfs:label
  • class_label_ratio — owl:Class entities with rdfs:label
  • property_label_ratio — Properties with rdfs:label
  • comment_coverage_ratio, domain_range_ratio
Why split? The aggregate label_coverage_ratio was always 1.0 (dominated by classes). Splitting exposes that property labelling is inconsistent — Llama-2-70B leaves 28% of properties unlabelled.

Layer 2 — Scenario Faithfulness

  • cq_coverage_ratio — CQs answerable (token overlap)
  • cq_mean_token_recall — Avg token recall per CQ
  • scenario_coverage_ratio — Scenario vocab in ontology
  • hallucination_ratio — Unsupported vocabulary fraction

Layer 3 — Semantic Similarity (vs Ground Truth)

  • class_name_F1 — Name match vs ground-truth classes
  • property_name_F1 — Same for properties
  • combined_f1 — Macro avg F1
  • matched_class_names — Classes in both generated & GT
  • matched_property_names — Properties in both
Matching: local name extracted, CamelCase split, case-folded. :hasCause ↔ "has cause".

Layer 4 — Feasibility & Unseen Analysis

  • Each (ODP, model) pair classified: plausible_unseen vs likely_seen
  • Compares ODP pub date vs model training cutoff
  • Confidence: high / medium / low
  • Future: human eval — Correctness, Completeness, Clarity (1–5)
Pipeline: evaluate_outputs.py → eval/formal_quality.py + faithfulness.py + similarity.py → results/summary.csv (420 rows × 44 columns)

Functional Evaluation — Utility-Oriented Pilot Assessment

Functional evaluation pilots a utility-oriented composite score, measuring whether generated ODPs answer CQs without adding unsupported ontological commitments. Applied to the best configuration per model family.

Scoring Methodology

functional_score = 0.5 × manual_score + 0.5 × cq_pass_rate

  • numb: total elements added beyond ground truth
  • numbnoscen: extra elements with no scenario grounding
  • superfluous_penalty = numbnoscen × 1.0 + (numb − numbnoscen) × 0.3
  • manual_score = 1 / (1 + 0.5 × superfluous_penalty)
  • cq_pass_rate: fraction of CQs answerable by the generated ontology

Unsupported additions penalized at 1.0; scenario-justified additions at 0.3 — reflecting differential harm.

Open-Source Model Selection for Human Evaluation

Structural and functional evaluations identify different open-source winners. Two configurations are selected for human evaluation to represent both quality dimensions.

Track A — Structural / Creativity Winner

Llama-3.1-8B + scenario-only

  • Structural score 0.595 — best open-source scenario-only result
  • OOPS score 0.405 — highest among open-source scenario-only runs
  • Parse rate 78.6% across 14 scenarios
  • Tests whether scenario text alone suffices for ODP generation
  • Richer ontological outputs; higher creativity
  • Trade-off: more superfluous additions than minimal configs

Track B — Functional Winner

Llama-2-70B + cq-only

  • Functional score 0.534 — highest among all evaluated configurations
  • CQ pass rate 0.202 — highest open-source cq-only result
  • Parse rate 85.7% in cq-only configuration
  • Average 0.79 extra elements: extremely minimal outputs
  • Structural quality known to be poor — "incredibly bad modeling"
  • Human experts will assess whether functional advantage survives scrutiny
Why two tracks? Structural metrics reward OWL correctness and expressivity; functional metrics reward minimalism and CQ answerability. The fact that they select different models is itself a scientific finding, motivating human evaluation to determine which dimension predicts real-world usefulness.
Evaluation design: Reducing to 2 open-source configurations (from 5) makes human evaluation feasible. The scenario-only vs. cq-only contrast also probes the extremes of the prompting spectrum for open-source LLMs.

Human Evaluation Plan

Expert and student evaluation of selected LLM-generated ODPs. Blind design: evaluators are not told whether an ODP was generated by an LLM or a human. Three evaluator groups receive tailored forms.

Pattern Authors

  • Intent match (1–5): Does the ODP model what the original pattern was designed to model?
  • Scope appropriateness (1–5): breadth — too broad / too narrow / right
  • Reuse readiness (1–5): ready for reuse without major modification?
  • Adoption threshold: Would you start from this draft rather than scratch? (Yes/Maybe/No)
  • Time saved vs from-scratch (0% / 1–25% / 26–50% / 51–75% / 76–100%)
  • Missing core elements: free text — essential classes/properties absent from the draft

Ontology Experts

  • Overall helpfulness (1–5): useful as a starting point for ontology design?
  • Reusability (1–5): reusable or adaptable in related contexts?
  • Clarity / Documentation (1–5): clear and complete accompanying documentation?
  • Adoption threshold: start from this draft or from scratch? (Yes/Maybe/No)
  • Time saved (0% → 76–100%)
  • Free text: observations, concerns, suggestions

MSc / PhD Students

  • Time to understand (minutes): includes reading scenario + CQs
  • Documentation clarity (1–5)
  • Naming clarity (1–5): intuitive and self-explanatory class/property names?
  • Adoption: start from this draft rather than scratch? (Yes/Maybe/No)
  • Time saved (0% → 76–100%)

Participant Pool

  • Pattern authors: ~2 (incl. 1 also a student)
  • Ontology experts: ~5 (some also pattern authors)
  • MSc/PhD students: ~2
  • ISWC workshop: ~8 (experts + students)
  • Target: ~38 expert evaluators + ~38 students
  • Each evaluator rates ~3 ontologies; authors rate ~2
  • Platform: odp-platform
Open questions: Very long CQ lists (e.g., 47 CQs for AISHIP) may deter participation — considering trimming to ~3 representative CQs per scenario. Whether to include ground-truth ODPs as a calibration item.
Blind design: Evaluators are told that ontologies could be either LLM-generated or human-authored. Source is not disclosed, reducing expectation bias.
ODP evaluated in pilot: Cultural Heritage Survey (2026-155-01) — one pattern author present for this ODP attended the pilot session.

  • 100% parse on every single configuration
  • Best CQ coverage and Combined F1 when successful
  • Trade-off: highest hallucination ratio (adds unsupported domain knowledge)

Key Findings

F1. Model size alone does not predict performance. Llama-3.1-8B (8B) outperforms Llama-2-70B (70B) on parse reliability.
F2. Gemini 3.1 Pro is the only model with 100% parse success across all configurations — but also the highest hallucinator (0.623).
F3. class_label_ratio = 1.0 for all models. property_label_ratio reveals hidden gaps — Llama-2-70B labels only 71.7% of properties.
F4. scenario-cq-reasoning achieves the lowest hallucination (0.461 avg) and best scenario coverage — best faithfulness-quality trade-off.
F5. BLOOMZ-7B1: 0% parse rate across all configs. Instruction-tuned BLOOM-family models still cannot produce valid OWL Turtle.
F6. Combined F1 is universally low (0.06–0.13) — LLMs diverge in naming conventions from expert ontologists even when semantically correct.
